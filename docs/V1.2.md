# Homeport 1.2 — plan

Four features, built in this order. Each one ships with tests, docs and a
changelog line; 1.2.0 is released when all four are done.

| # | Feature | In one line |
|---|---|---|
| 1 | **`homeport.json` team setup** | One file in a repo describes its apps, databases and start order; anyone gets the whole setup in one click. |
| 2 | **PR previews + comments → issues** | Run a pull request next to your copy and share it on the PR; turn a visitor comment into a GitHub issue. |
| 3 | **First-run welcome** | A 3-step start for new users instead of an empty page. |
| 4 | **Local HTTPS** | Open apps at `https://shop.localhost` with a trusted local certificate — no change to the app. |
| 5 | **Notify on new comments** | A desktop notification when a visitor comments or replies on a shared link. |

Same principles as before: optional, no Homeport account, nothing in the
cloud, nothing runs or changes without the user seeing it first.

## 1. `homeport.json` — team setup

### The file

Lives in the root of a repo (committed with the code):

```json
{
  "name": "Shop",
  "services": ["postgres", "redis"],
  "apps": [
    {
      "name": "API",
      "path": "api",
      "command": "php artisan serve --port {port}",
      "port": 8000,
      "env": { "DB_PORT": "{postgres.port}", "REDIS_URL": "{redis.url}" },
      "health": "/up"
    },
    { "name": "Web", "path": "web" }
  ]
}
```

| Field | Meaning |
|---|---|
| `name` | The project. Becomes the apps' category (a workspace: start/stop together, in order). |
| `services` | Databases to add: `postgres`, `mysql`, `redis`, `mongodb`, `mailpit`. An existing one of the same kind is reused. |
| `apps[]` | In start order. `path` is relative to the file (`.` for the root). |
| `command` | Optional — left out, Homeport detects it like *Add app*. `{port}` is the app's port. |
| `port` | Optional — a free port is picked if it's taken. |
| `env` | Extra variables. `{postgres.port}`, `{postgres.url}`, `{redis.host}` … fill in the service's real values. |
| `health` | Optional path checked to know the app is up (e.g. `/up`). |
| `auto_restart` | Optional `true`. |

Unknown fields are ignored (forward compatible). Paths can't leave the repo
folder (`..` is refused).

### Using it

- **Add app → folder**, **Discover projects** and **Add from GitHub** notice a
  `homeport.json` and offer **Set up from homeport.json**.
- A review screen lists every app with **the exact command it will run**, the
  databases, and the start order. Nothing is added or run until the user
  clicks **Set up** — a repo's file is someone else's code.
- Apps already added (same folder) are skipped, not duplicated.
- *Start after setup* starts the whole group in order.

### Making one

Category heading → **Save as homeport.json** (or ⌘K). Homeport writes the
file into the folder that contains all of the group's apps, with relative
paths, detected commands left out when they match what Homeport would detect,
and service values turned back into placeholders. It shows the file first and
never overwrites one without asking.

### API

| Method | Path | |
|---|---|---|
| GET | `/api/project?path=` | read + check a `homeport.json`: apps (resolved paths, commands, ports), services, warnings |
| POST | `/api/project/setup` | `{path, start}` → add services and apps, optionally start the group |
| POST | `/api/project/export` | `{category, write}` → the file's content (and write it) |

## 2. PR previews + comments → issues

(GitHub phases 2 and 3 — see `docs/GITHUB.md` §3–4.)

- **Preview a pull request.** On an app from GitHub: ⋯ → *Pull requests* →
  *Preview #42*. Homeport adds a **git worktree** of the PR's branch next to
  the repo (`<repo>-pr-42`), adds it as an app on its own port (same command,
  same env), and starts it. Your working folder is never touched. *Remove
  preview* stops it and deletes the worktree.
- **Share on the PR.** *Share preview on PR* starts a share link (feedback on)
  and posts it as a PR comment — after showing the text.
- **Comment → issue.** In the Feedback window each comment gets *Create
  issue*: title from the comment, body with the page, screen size, thread and
  a link back; Homeport shows the issue before creating it and remembers the
  link on the comment.
- Needs a GitHub connection with `repo` scope (already asked for).

## 3. First-run welcome

When Homeport has no apps yet, the empty page becomes a short welcome:

1. **Add your projects** — *Scan a folder* (Discover) or *Add one app*.
2. **Connect GitHub** (optional) — *Add from GitHub*.
3. **Pick your AI** (optional) — Claude Code if found, or set up a local model.

Each step can be skipped; the welcome disappears once an app exists (and can
be reopened from ⌘K → *Getting started*).

## 4. Local HTTPS

- One switch per app (Edit → *HTTPS*) and a default in Settings.
- First use: Homeport creates **its own local certificate authority** (kept in
  the data folder, private key mode 600) and asks the system to trust it
  once (macOS: Keychain prompt; Windows: certificate store prompt; Linux: the
  steps for the browser/NSS store are shown).
- Homeport's proxy serves `https://<app>.localhost:<port>` with a certificate
  for `*.localhost` signed by that CA; the app keeps running on plain HTTP
  behind it — no framework changes. Live reload (WebSockets) keeps working.
- Phone preview can use HTTPS too (certificate for the LAN address), so
  camera/location/PWA features work on the phone after trusting the CA there.
- *Remove local certificates* in Settings deletes the CA and asks the system
  to forget it.
- The CA never leaves the computer; it's only valid for `localhost` names and
  the LAN address.

## 5. Notify on new comments

- When a visitor posts a comment or a reply on a shared link, Homeport shows a
  desktop notification: *“Maria commented on Clipio: Can this button…”*.
- Settings → Sharing & feedback → *Notify me about new comments* (on by
  default). Comments you write yourself (review mode, Feedback window) don't
  notify.
